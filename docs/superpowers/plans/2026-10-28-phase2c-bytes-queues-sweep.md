# Phase 2c: Byte Flows, Queues and Workers, External Sinks, Sweep — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Bytes become first-class and asynchronous work runs. After 2c every op can state its size, blob stores and byte-sized CDNs are checked and run in bytes (the `not checked` lines of 2b become verdicts), a link's `bandwidth` is a pipe that queues and drops; a `message_queue` holds what its consumer `worker_pool`s have not drained, the pools work at `workers / cost` and run `then` steps, and the publisher never waits for them; `external_sink`s answer slowly and fail a fraction; `kv_cluster`s run their ring, replication and quorum latency; the 2b backlog lands (a step after a failed step does not run, a client's `timeout` turns its slow tail into unanswered requests, SLOs can be checked per window with `over:`); and `simsys sweep` runs one scenario over a range of one key and prints a table. Three more book systems run end to end with README numbers: **youtube**, **news-feed** and **search-autocomplete**, plus `labs/kv-store`. **chat-system**, **google-drive**, **notification-system** and **web-crawler** stay for phase 3 (they need `ws_gateway`, `service_discovery`, `notification_fanout` or `frontier`).

**Architecture:** One new module, `simsys.sweep` (parameter ranges, scenario overrides, points run on `std::jthread` workers, the result table), with its thread code in an implementation unit. Byte flows need no module of their own: `simsys.core` gains `Bytes` and the size grammar, the graph resolves one request size per (node, op) at build (as it resolves che keys), and a byte-sized node or link counts **megabytes as its capacity units** through the existing op-cost machinery, so the fluid queue, Erlang C and the reports need no second unit system. Five behaviours join the variant (`BlobStoreBehaviour`, `MessageQueueBehaviour`, `WorkerPoolBehaviour`, `ExternalSinkBehaviour`, `KvClusterBehaviour`); `search_index` is a `ServiceBehaviour` like the id generator; a bandwidth link gets a fluid queue of its own in the engine.

**Tech Stack:** unchanged (C++23, GCC 14.2, CMake 3.28 modules, Catch2 3.7.1, yaml-cpp, CLI11). New standard facilities: `<thread>`'s C++20 `std::jthread` (joining destructor) with `std::atomic<std::size_t>` as a work counter for the sweep, and `std::thread::hardware_concurrency`; `std::erfc` for the normal CDF (C++11, no first-use comment needed). Each C++20/23 first use gets its comment; `docs/study/threads.md` is new. `<thread>` includes `<chrono>`, so it goes in `src/sweep/sweep.cpp`, never in an interface that imports a module (first GCC 14.2 defect).

**Conventions:** as in the 2b plan (TDD split: a test-writer commits the failing tests as `test(<area>): <subject> (TDD red)`, an implementer makes them pass with the minimum and commits the message given in the task, an adversarial reviewer reviews in its own git worktree, and the fix round is recorded in this plan as a "Review of …" section under the task; each concurrent agent in its own build directory, `build/gcc14-<task>` and `-rel`; stage by file name only; no `[` or `]` in test names; tight numeric checks with `WithinRel`/`WithinAbs`; the four GCC 14 workarounds: no `<chrono>`/`<filesystem>`/`<format>`/`<print>`/`<thread>` in an importing interface's global module fragment, `std::to_chars` and hand padding instead of format widths, `-fno-ipa-sra` and `-flarge-source-files` kept, a new `emit_special_members` line in `src/model/model.cpp` when a new model member breaks the Release link). Every task that changes which shipped scenarios run updates the runnable-set test in `tests/scenario/test_scenarios.cpp` by name.

**Spec refinements made here (spec §19 in Task 19):**

1. **Request sizes, resolved once.** A client's `sizes: {op: size}` gives each op it sends a size in bytes (`200B`, `2KB`, `50MB`, `1.5GB`; decimal, as the byte-rate grammar: 1 KB = 1000 B). A step may state `size:` (a worker's or service's request that carries its own payload). A request keeps its size while it keeps its op name: through a balancer's or limiter's routes, a cache's or CDN's miss and write forwarding, and a step whose `op` is the incoming op (stated or defaulted). A renamed op without `size:` is unsized. The graph resolves one size per (node, op) at build (`Graph::request_bytes`); two different sizes reaching the same (node, op) are an error naming both senders (as two key distributions are, §18 entry 1), and so is an unsized op reaching a **byte-sized node** or a **bandwidth link**: `node 'transcoded_store' counts bytes (capacity 10GB/s), but op 'write' from 'transcoders' has no size: add size: to the step or sizes: to the client`. A request-counting node never needs a size. *Why static:* every shipped scenario sends one size per (node, op); a flow that carries bytes per op (spec §3.2) is the general form, phase 3. *Ignores:* a size distribution (each op's size is its mean), headers and protocol overhead, compression.
2. **Byte-sized nodes count megabytes.** A node is byte-sized when its capacity is a byte rate: a stated `capacity: 100GB/s` (any `cdn`, `blob_store`), or a `blob_store`'s default (spec §6: 500 MB/s). Its capacity unit is **1 MB** (`defaults::byte_unit = 1e6`, replacing 2b's `blob_object_bytes` assumption): `capacity` = bytes/s ÷ 1e6 units/s, and a request of op `o` costs `request_bytes(o) / 1e6` units, through the existing per-op cost (§17 entry 4). Its `latency` is the time to serve **one megabyte** (defaults: a CDN `network_read_1mb` = 10 ms, a blob store `disk_read_1mb + network_read_1mb` = 40 ms, both spec §6), so the implied concurrency is Little's law again, `c = capacity units/s × s`: `cdn_us` 100k MB/s × 10 ms = 1000 transfers at once, `original_store` 5k MB/s × 40 ms = 200. A request's **sojourn is its wait plus one unit's time** — its time to first byte — as a SQL write of cost 5 uses more capacity but not a longer sojourn (§18 entry 7). Worked: a 100 GB/s CDN saturates at 100e9 / 50e6 = **2k streams/s** of 50 MB; youtube's 281.6 streams/s at the 21:00 peak are 14.08k MB/s, **14.1 %** of `cdn_us`. *Ignores:* the transfer time of the rest of the object (a 300 MB upload at 25 MB/s takes 12 s; the response time reported is the first megabyte's), that a request's megabytes arrive together (an M^X batch, which waits longer than the Poisson units the queue assumes), and that a request under 1 MB still pays one unit's time (an upper bound for small objects: a 2 KB read from a blob store costs 0.002 units but 40 ms). *Corrected by the review of Task 3 (I1, I2, below):* the queue waits for whole objects (Erlang C fed the rate-weighted mean object time, the same c), a write (`write_ops`, now a blob store key) is answered at its last byte and a read at its first megabyte.
3. **A link's `bandwidth` is a pipe** (spec §3.4, "caps bytes/s and queues the excess like a node"). `bandwidth` is a byte rate, also in bits: `40Gbit/s` = 5 GB/s (÷ 8). The pipe is one server (`c = 1`) whose unit is 1 MB served in `1 MB / bandwidth` (8 ms at `1Gbit/s`), deterministic (service SCV 0, so Kingman's factor is `(burstiness + 0)/2 = 0.5`: M/D/1 for Poisson arrivals), with a waiting room of 1000 MB (chosen: the generic `queue_limit` default read in units) beyond which it drops. A request holds the pipe for its whole serialisation (`size × 1 MB / bandwidth`), so the queue waits for whole requests. A hop over the link adds, once, the pipe's wait plus the request's answer time on the wire, by refinement 2's rule for the node behind it (*amended by the review of Task 5, I-2*): a **write** (an op in the receiver's `write_ops_of`; *amended by the review of Task 6, I-2:* decided per (link, op) at build, an op is a write on a link if the receiver or any node it reaches from there under its own name lists it, so a balancer in front of the store changes nothing; *amended by the review of Task 7, I-2:* or under the new name of a step that states its own `size:`, which forwards the body) its whole serialisation, since the receiver acts after the last byte, and **any other op** its first megabyte, `min(size, 1 MB) × 1 MB / bandwidth`, since the receiver answers at its first megabyte while the rest streams in; a streamed PUT into a blob store therefore pays the wire's and the disk's whole-object times in series (an upper bound: pipelining is ignored). Its losses multiply the hop's delivered fraction. Worked: 1 MB objects at 100/s over `1Gbit/s`: serialisation 8 ms, rho 0.8, Wq = 0.5 × 0.8/0.2 × 8 ms = **16 ms**, sojourn 24 ms; 10 MB at 10/s: Wq 160 ms, a read's hop 168 ms, a write's 240 ms. **Direction** (*review of Task 5, I-1*): the pipe is fed by the demand that crosses the link, each request charged its whole stated size in the demand direction whichever way its bytes travel; replies add no bytes, so an `inout` link is one pipe, and `x->y` and `y->x` with a bandwidth are two pipes. Reports get one row per bandwidth link, named `from->to` as written (also for `dir: in`). *Ignores:* the true direction of each byte (above), TCP slow start and window limits, packet loss and retransmission, protocol headers, the link's propagation delay changing with load; the wait is capped at the room's drain time (1000 MB / bandwidth), which understates it for requests larger than the room.
4. **A message queue is a broker plus the waiting room of its consumers.** The `message_queue` node is the broker: its own queue is the append (spec §6: 1M msg/s, 100 µs chosen), and a publisher's request is answered when the message is appended. Every link out of a queue must go to a `worker_pool` that `consumes` it, and every such consumer group receives **every** message the broker appended (Kafka's consumer groups; google-drive's two groups on `notify_q` read it so). The messages a group has not drained wait **in that group's pool queue**, whose waiting room is the queue's `retention`: `queue_limit = retention × the pool's capacity` (messages older than `retention` are deleted unconsumed and counted as the pool's drops); `retention` defaults to 7 days (Kafka's `log.retention.hours = 168`, an industry default: the book gives none). The **queue lag** of a group is its wait: `lag = max(backlog / drain, k × Wq)` — the fluid part is the FIFO drain time (backlog over drain rate: the oldest message waits for everything ahead of it to drain; *wording corrected by the review of Task 6, M-7*, it said Little's law), the stochastic part the pool's Allen–Cunneen M/M/c wait of refinement 5; a queue's lag is its worst group's. `partitions` is accepted and printed, not modelled (see the Phase 3 backlog). *Ignores:* ordering, delivery guarantees and redelivery, a consumer's commit interval, the broker's disk.
5. **A worker pool is M/M/c over consumption** (spec §7: "capacity = workers / job cost"). `c = workers`, service time `s = cost` (a duration per job), capacity `workers / cost` jobs/s: youtube's 400 transcoders at 60 s are 6.67 videos/s. `capacity`, `latency`, `replicas`, `advanced.concurrency` and `advanced.queue_limit` on a pool are refused (each restates `workers`, `cost` or the queue's `retention`). Worked: 1k msgs/s into 4 workers of 300 jobs/s each (cost 3.333 ms): rho = 1000/1200 = **0.8333**, Erlang C(4, 0.8333) = 0.6577, Wq = 0.6577 × 3.333 ms / (4 × 0.1667) = **3.289 ms**, sojourn 6.622 ms. A job's `then` steps (sequential, parallel, `factor`, `size`) carry each drained job on, like a cache's `then` (§18 entry 5). A worker is busy for `cost` only: its `then` hops do not hold it. *Ignores:* a worker blocked on a slow downstream call (an external sink's 150 ms would cut a pool's real capacity: phase 3 backlog), autoscaling, poison messages.
6. **Asynchronous completion.** The hops from a queue to its consumers and a blob store's `then` hops are asynchronous (`Graph::async_hops`, as write_back flushes are, §18 entry 5): the sender's response and delivered fraction end there, so a publisher waits for the append alone and an uploader for the store alone; losses beyond (a full pool, a failed sink) count in those nodes' drop rates and not in the client's answered rate. No shipped scenario has a client waiting for a worker's answer, so a synchronous request/reply over a queue is phase 3. *Ignores:* the end-to-end completion time of the asynchronous work (upload → playable); the queue lag is what the SLOs check.
7. **A blob store's `then` steps are event notifications** (S3 event notifications, ch. 14's "transcoding starts when the upload completes"): they fire for every request the store served, asynchronously (refinement 6), carrying the op the step names: a same-op `then` step inherits the incoming size (refinement 1); a renamed step is sized by its `size:` or unsized. *Ignores:* event batching and delivery delay, failed notifications.
8. **External sink.** A third party's API as a queue of the type's numbers (capacity 1k/s chosen: the quota a provider gives one account; latency 100 ms and service SCV 2.0, spec §6 `third_party_api`); `failure_rate f` fails that share of what it served: `dropped += f × served`, `drain = (1 − f) × served` (so `demand·dt = (drain + dropped)·dt + Δbacklog` still holds), and its own delivered share is `1 − (dropped + rejected)/inflow` as for any node. Failures are drops: the node failing (a 5xx from the provider), not a policy. Worked: 500/s into a sink with `f = 0.02`: 490/s answered, drop rate **0.02**, sojourn 100 ms (C(100, 0.5) = 3.3e-10: no wait), variance 2 × (100 ms)² = 0.02 s². `politeness` is accepted and printed, not modelled (it needs per-host state: phase 3 with `frontier`). *Ignores:* retries (phase 3: `on: failure` steps still never fire), a provider's latency rising with our load beyond its queue.
9. **kv_cluster, steady state** (spec §7 row; ch. 6). `nodes` machines of `capacity` each, on a ring; every request goes to its key's `replication` N replicas (Dynamo's coordinator sends reads and writes to all N, ch. 6 "quorum consensus"), so the cluster's demand is `N ×` the requests and each node averages `rate × N / nodes`; with `N < nodes` the hottest node carries `1 + 1/√vnodes` × the average (the balancer's ring heuristic, §17 entry 5, as hot and cool copy groups, §17 entry 9), with `N = nodes` every node holds every key (no imbalance). The response of a read is the **R-th fastest** of N replica sojourns (W-th for a write, ops in `write_ops`): with each sojourn exponential of the copies' request-weighted mean `m`, the k-th order statistic of N iid exponentials has (Rényi's representation) mean `m Σ_{i=0}^{k−1} 1/(N−i)` and variance `m² Σ_{i=0}^{k−1} 1/(N−i)²`. Worked, N = 3: R = 1 → 0.3333 m (variance 0.1111 m²), R = 2 → **0.8333 m** (0.3611 m²), R = 3 → 1.8333 m (1.3611 m²). `replicas` on a kv_cluster is refused (its machines are `nodes`); `mode: ap|cp` is read and printed, and matters only under partitions (phase 3). *Ignores:* partitions, sloppy quorum and hinted handoff (faults: phase 3), read repair and anti-entropy traffic, vector clocks, the replicas' sojourns not being exponential when `c > 1` or the service SCV is not 1.
10. **search_index serves like a service** (spec §7: "read-mostly capacity; build-vs-serve split"): a `ServiceBehaviour` with no steps and the type's numbers (5k/s, 5 ms, chosen) unless stated, as the id generator is service sugar (§18 entry 12). `build_interval` is read and printed; the periodic rebuild's load is not modelled. *Ignores:* index build load, index freshness.
11. **A step after a failed step does not run** (2b backlog). In an op's step list (a service's, a worker's `then`, a cache's `then`), the flow sent on step `k` is `rate × fraction × factor × S_k`, where `S_k` is the product, over the sequential hops and parallel groups before it, of their **delivered** fraction `d` (a parallel group delivers the product of its branches' `d`: one failed branch fails the op; its branches all start together, so each receives the same `S`); a miss block passes `h + (1 − h) × Π d_block` of the requests on. The `d` are the previous step's (the backward pass runs after the forward pass): a failure thins the steps after it one step late, and `estimate`'s settle passes reach the fixed point. The op's own delivered fraction was already the product and does not change. Worked: 1k/s through steps `[a, b]` with `a` delivering 0.5 sends `b` **500/s**; through `[a ∥ b, c]` with `a` at 0.5 and `b` at 0.8, `c` gets **400/s**. *Ignores:* a step that fails after the next one started, partial work of a failed request.
12. **Client timeout.** Each step, a client op's response is a lognormal fitted to its mean `m` and variance `v` (`σ² = ln(1 + v/m²)`, `μ = ln m − σ²/2`, as reports already fit it); with `timeout: τ` the share answered in time is `Φ(z)`, `z = (ln τ − μ)/σ`, and it multiplies the op's delivered fraction; the answered requests' moments are the lognormal's partial moments below τ, `E[T | T ≤ τ] = m Φ(z − σ)/Φ(z)` and `E[T² | T ≤ τ] = e^{2μ + 2σ²} Φ(z − 2σ)/Φ(z)`, and reported percentiles are capped at τ (the refitted lognormal has a tail past it). Worked: m = 100 ms, v = 0.01 s² (CV 1: σ = 0.8326, μ = −2.6492), τ = 200 ms: z = 1.2488, **89.41 %** answered (10.59 % time out), answered mean **73.97 ms**; τ = 1 s: 99.927 %; τ = 50 ms: 33.86 %. Servers still do a timed-out request's work (nothing cancels it) and nothing retries (phase 3). JSON's ops gain `timed_out_per_s`. *Ignores:* timeouts at intermediate hops, that a path is not exactly lognormal.
13. **SLOs per window: `over: D`.** Any SLO may state `over` (a duration, at least one step, at most the observed span): the observed span after warmup is cut into consecutive windows of `D` aligned to the end of warmup (a last, shorter window is evaluated like the rest), the metric is computed per window exactly as over the whole span (a percentile from the window's answered-weighted moments, a utilization as the window's mean busy fraction, ...), the SLO observes the **worst** window and fails if it fails; a window in which the client offered nothing is skipped. Worked: a 2k/s service at rho 0.5 for an hour with a 1.8× spike for 10 minutes from 00:20: whole-hour utilization **0.5667** passes `max: 0.8`; `over: 10m` observes **0.9** and fails; `over: 15m`, 0.7667. A zone SLO (`metric: zone`) is not added: a windowed utilization says the same in numbers. *Ignores:* sliding windows.
14. **`queue_lag` SLO.** `node` is optional and must be a `message_queue` (the worst queue without it); the observed value is the queue's **peak** lag after warmup (refinement 4), since a lag bound is a bound on the worst moment; `over` adds nothing to it. JSON nodes gain `peak_queue_lag_s` (`null` for other nodes), the CSV series a trailing `queue_lag_s` column (empty for other nodes), the table a `peak_lag` column.
15. **`simsys sweep`** (spec §11's subcommand): `simsys sweep <file> --param <key>=<from>..<to>:<n> [--metric <m>]... [--jobs N] [--report table|csv]`. `n ≥ 2` points, evenly spaced, both ends included, in the endpoints' kind and unit (a rate, byte rate, duration, size or count; both ends the same kind; a count must give whole numbers: `400..600:3` is 400, 500, 600, `400..600:4` is an error). The key is a dot path through the YAML maps of the file (`nodes.users.rate.base`) and must exist; each point is the file with that one scalar replaced, loaded and validated like any scenario (`config::load(path, overrides)`), then `run` over its whole duration. Points run in parallel on `std::jthread` workers (`--jobs`, default the hardware threads), each a `Simulation` of its own, so the output is byte-identical whatever `--jobs`. Columns: the value; each `--metric` (`users.p99` a client's worst p99, `users.read.p99` one op's `p50|p95|p99|mean`, `api.mean_rho`, `api.peak_rho`, `api.drop_rate`, `api.reject_rate`, `q.lag`); each SLO's observed value and verdict; the point's run exit code. Exit 0 when every point ran (verdicts are data here), 1 on a load or build error, which names the point. *Ignores:* grids over two keys, geometric spacing, list values, replications per point (phase 3).
16. **Step size rule of thumb** (2b backlog; docs only). A token bucket of `B` tokens under an offered rate `λ` above its limit `L` empties in `B / (λ − L)`; a step longer than that passes the whole burst in its first step and the bucket's shape vanishes (a 2,000-token burst at `step: 1s` does). Rule: `step ≤ B / (λ_peak − L)`, and for queues `step ≤` a tenth of the shortest spike. Written in `docs/study/numerics.md` and the schema's `step` row.

- **Types:** `ws_gateway` (connections as a level, session fan-out: chat-system, google-drive), `service_discovery` (lookup latency, failover: chat-system), `notification_fanout` (channels, dedup, retries with a dead-letter queue: notification-system), `frontier` and an external sink's `politeness` (per-host state: web-crawler).

- **Faults and retries:** the `faults` list, retry feedback (`retries`), `on: failure` steps, external failures retried (notification-system's `drop_rate` SLO cannot pass without them).
- **Queues:** `partitions` bounding a consumer group's parallelism (`c = min(workers, partitions × consumers per partition)`; youtube's 32 partitions would cap 400 transcoders); a request/reply over a queue (the client waits for the worker); the end-to-end completion time of asynchronous work; a worker blocked on its `then` hops (an external sink's latency holding a worker).
- **Bytes:** bytes carried in the flow (spec §3.2) so that one (node, op) may mix sizes by rate; a large read's last byte (a read is answered at its first megabyte, which understates a download needed whole before use; writes already answer at their last byte); batch arrivals of a request's megabytes (M^X/D/1); full-duplex links.
- **The stochastic wait's utilization in a transient** (review of Task 3's second fix round at 9a547e2, I-3): the Erlang term reads rho = drain / capacity, which stays 1 while a full room drains after the load falls, so the wait holds at the room's drain time instead of falling with the backlog. Candidate: `rho_stoch = min(demand, drain) / capacity`.
